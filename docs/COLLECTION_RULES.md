# 采集器铁律（不可违反）

> 立规时间：2026-10-02。由用户明确指令确立。
> 本文档是**约束**，不是建议。任何采集相关工作开始前必须先读本文档。

---

## 规则 1：禁止接口级压测

**绝不允许**对任何真实站点接口做高频/连续/探索性调用。

### 禁止行为（全部实测过，全部造成过伤害）

| 禁止 | 说明 |
| --- | --- |
| 连续循环调用同一接口 | 曾在 BOSS `/wapi/zpgeek/search/joblist.json` 连发 8 次 |
| 试探性请求（探边界/探参数） | 曾用不同 header、`pageSize=30`、多页翻页做"可行性验证" |
| 对同一账号做对照实验 | 曾用同一登录态反复重试以区分"限流 vs 封禁" |
| 未定预算的爬虫 | 任何没有明确次数上限的采集脚本 |

### 事故记录

对 BOSS 列表接口连续调用后，返回码出现**升级**：

```
前 3 次：code=0      成功，15 条
第 4 次起：code=37   "您的环境存在异常"
最后：    code=36   "您的账户存在异常行为"   ← 从「环境」升级为「账户」
```

`code:36` 是**账号级**风控。虽然账号未被封（`getUserInfo` 仍返回 `code:0`），但已留痕。

> 教训：**在只有单账号的情况下，任何高频调用都是在拿账号做赌注。**

## 规则 2：所有接口爬虫必须先定预算

任何接口采集脚本，**在第一次请求之前**必须明确声明并写入代码：

| 必须声明 | 示例 |
| --- | --- |
| **总请求数上限** | `MAX_REQUESTS = 20` |
| **请求间隔下限** | `MIN_INTERVAL_MS = 3000` |
| **单次运行时长上限** | `MAX_DURATION_MS = 120000` |
| **遇到风控码时的动作** | 立即停止，不重试、不降级试探 |
| **并发度** | 默认 1（串行），禁止并发 |

### 风控码处理（一律硬停）

| 码 | 含义 | 动作 |
| --- | --- | --- |
| `code:37` | 环境异常 | **立即停止本次运行**，记录，不重试 |
| `code:36` | **账户异常行为** | **立即全局停止**，通知用户，当日不再调用 |
| `code:7` | 登录失效 | 停止，提示用户重新登录 |

**禁止**：遇到风控码后更换 header/cookie/参数继续重试——这既是压测，也是规避风控。

### 站点自愈窗口（等待，不重试）

安全校验由网站自己走完时，采集器**等待**而不是重试。等待期间不发任何指令，请求数增量为 0，因此不计入重试预算，但必须有上限。

| 平台 | 站点 | 等待窗口 | 依据 | 边界 |
| --- | --- | --- | --- | --- |
| BOSS | `/web/passport/zp/security.html?code=37` | **15000 ms** | 2026-10-02 实测该跳约 12 秒由网站自行走完并返回列表；原 8 秒窗口总在完成前一刻到期 | 仅首次列表页允许；进入详情页后安全页仍是终态；全程只允许一次 |
| BOSS（Playwright 路线） | 同上 | 8000 ms | 历史契约，未在原生路线实测 | 同上 |
| 猎聘 | `safe.liepin.com` | **0 ms** | 验证需人工点击，且登录本身会触发账号风控 | 即时终止 |

窗口到期或第二次进入安全页，一律按 `code:37` 处理：立即停止，不重试。

### 接口限流预算（四大厂 provider）

零认证的公开 API 同样受规则 1 约束：慢一点，但**必须比通用 provider 更慢**——它们是同机房后端，不是给脚本用的开放 API。

| provider | 站点 | 页间隔 | 429 退避 | 空响应保护 |
| --- | --- | --- | --- | --- |
| `alibaba` | talent.alibaba.com | **1200 ms** | 3 次 / 1.5s→20s | **有**：后续页返回 HTTP 200 + 空 `datas` 会被当成功吞掉，退避后重试该页 |
| `tencent` | careers.tencent.com | **1200 ms** | 3 次 / 1.5s→20s | — |
| `meituan` | zhaopin.meituan.com | **1200 ms** | 3 次 / 1.5s→20s | 已有 `EMPTY_RETRIES`（原为 400ms 间隔，本次一并放宽） |
| `feishu-jobs` | jobs.bytedance.com | **1500 ms** | 3 次 / 2s→30s | — |

**事故记录 2026-10-02**：四个大厂接口连续探测，前三个正常，飞书下一次请求返回空体。两次单页请求相隔仅数秒，已证明其限流是短窗口且与页大小无关——固定 300ms 间隔无法防御，这也是把间隔提到 1.2–1.5s 的直接依据。

**阿里空响应是最危险的一处**：它的边缘层被限流时返回 `success: true` 但 `content.datas` 为空。若不处理，一次 40 页的整板抓取会在第 2 页被误判为"关键词已到末尾"而静默截断。现已改为：第 1 页允许为空（非真实关键词的正常情况），后续页在满页之后转空则按限流签名重试。

**通用要求**：

- 页间隔跨页、跨关键词生效，首个请求不等待
- 429 必须走 `_http.mjs` 的 `fetchJsonWithRetry`（识别 `Retry-After`、指数退避），**禁止裸 `ctx.fetchJson`**
- 4xx（非 429）不重试——重试一个格式错误的请求只是浪费预算
- 上述每条都有对应回归：`tests/providers/{alibaba,tencent,meituan,feishu-jobs}.test.mjs` 中的 429 / 空响应用例

### 浏览器平台限流预算（BOSS / 猎聘 / LinkedIn）

> **2026-10-02 补记。此前这一层是空的，而它正是风控累积的原因。**

driver 上的 `delayMs` 是**页面就绪等待**（轮询到安全页消失为止），**不是两次平台动作之间的间隔下限**。而 `china/collector.mjs` 的岗位循环原本**完全没有节流**——BOSS 的 `detail()` 正常路径（点击卡片 + 读面板）根本不经过 `wait()`，所以一次采集就是 N 次点击首尾相接。这是把 `_security_check` 计数推到 4+ 的机制性原因，不是偶发。

| 项 | 值 | 说明 |
| --- | --- | --- |
| 动作间隔 | **`--delay-ms`，默认/最低 15000 ms** | 用户声明的预算，逐字生效；覆盖列表页、每个详情页、每次翻页 |
| 首个动作 | 不等待 | 节流约束的是速率，不是启动 |
| BOSS 安全页冷却 | 15000 ms | 与「站点自愈窗口」同值，网站约 12s 自愈，这里只是下限 |
| 猎聘安全页冷却 | **0 ms** | 验证需人工点击，登录本身即可能触发账号风控，driver 直接终止（见规则 2.1） |
| LinkedIn | 同 BOSS | |

**实现**：`china/rate-limiter.mjs`，导出 `createRateLimiter({platform,intervalMs,challengeCooldownMs,now,sleep})`。`now`/`sleep` 可注入，因此全部 9 个测试瞬时完成、不做真实等待。

**关键点**：

- 无论是否需要等待，**每个动作都要打时间戳**。空闲后恢复工作的第一次请求若不记录起点，会与下一个请求首尾相接——限流器会形同虚设（此缺陷由 `pending()` 用例暴露并已修）。
- 遇到安全页时 `noteChallenge()`，冷却从**安全页被看到的那一刻**起算，不是从等待结束起算。
- 连续采集（`china/continuous-collection.mjs`）应把**同一个 limiter 实例**跨轮次传入，否则每轮各自重置时钟，轮次边界仍会紧挨。
- 429 退避（`providers/_http.mjs` 的 `fetchJsonWithRetry`）**对浏览器路线不适用**：BOSS 和猎聘被限流时返回的是安全页跳转，没有状态码可读，也就无 `Retry-After` 可依。浏览器路线的唯一控制手段就是这个间隔下限。

**回归**：`tests/china/rate-limiter.test.mjs`（9 例）。

## 规则 2.1：猎聘当前可用边界（2026-10-02 实测）

猎聘登录态已建立，但**账号 IP 已被站点安全中心拦截**，详情页采集暂停。

| 能力 | 状态 | 证据 |
| --- | --- | --- |
| 出口 IP 直连封禁 | ✅ 已解决 | mihomo 增加 `DOMAIN-SUFFIX,liepin.com,ExternalProxy`，实测走代理 7.3s vs 直连 0.47s |
| 列表页读取 | ✅ 可用 | 单次运行筛出 36 个岗位（9 采集 / 27 排除 / 4 待审） |
| 详情页读取 | ⛔ 暂停 | 页面本身可解析（实测 2732 字符完整 JD），但账号 IP 被拦截 |
| 会话 Cookie 持久化 | ✅ 已补齐 | 原实现只支持 BOSS 域名，猎聘登录态无法保存；已改为平台作用域 |

**事件记录**：2026-10-02 19:09，猎聘安全中心返回「您的ip被拦截，已被暂访问」。触发条件为登录动作本身叠加代理出口 IP。教训：登录前应先确认出口 IP 的信誉，不要在风控站点上用数据中心的代理 IP 建立会话。

**恢复条件**：换用未被封禁的住宅网络出口，并先在正常浏览器确认账号可用，再谈采集。

## 规则 3：优先浏览器路径，不走接口

采集**优先使用浏览器路径**（真实登录态 + 扩展 / 页面内读取），因为它：

- 走的是官方允许的页面上下文；
- 不触发接口层签名校验；
- 风险留痕方式与人工浏览一致。

**接口重放已实测不可行**（见 `docs/career-ops-linux-migration-plan.md` §3.3），且会伤账号。**除非用户明确书面要求并自担风险，否则不使用。**

---

## 规则 4：采集范围不得缩减

迁移到 Linux 后，采集覆盖**必须与 Mac 上保持一致**：

- BOSS ✅
- 猎聘 ✅（当前受 IP 封禁阻塞，需解决而非放弃）
- 上游原有的其他采集器（76 个 provider 模块等）✅

**不得**以"某站难做"为由缩减范围——应报告阻塞并寻求解决。
