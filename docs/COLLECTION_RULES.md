## 规则 1：禁止接口级压测

**绝不允许**对任何真实站点接口做高频/连续/探索性调用。

### 禁止行为（全部实测过，全部造成过伤害）

| 禁止 | 说明 |
| --- | --- |
| 连续循环调用同一接口 | 曾在 BOSS `/wapi/zpgeek/search/joblist.json` 连发 8 次 |
| 试探性请求（探边界/探参数） | 曾用不同 header、`pageSize=30`、多页翻页做"可行性验证" |
| 对同一账号做对照实验 | 曾用同一登录态反复重试以区分"限流 vs 封禁" |
| 未定预算的爬虫 | 任何没有明确次数上限的采集脚本 |

### 事故记录

对 BOSS 列表接口连续调用后，返回码出现**升级**：

```
前 3 次：code=0      成功，15 条
第 4 次起：code=37   "您的环境存在异常"
最后：    code=36   "您的账户存在异常行为"   ← 从「环境」升级为「账户」
```

`code:36` 是**账号级**风控。虽然账号未被封（`getUserInfo` 仍返回 `code:0`），但已留痕。

> 教训：**在只有单账号的情况下，任何高频调用都是在拿账号做赌注。**

### 规则 1.1：间隔要随机，不能是定时的

**固定间隔本身就是一种规律**，而且规律是可以被写进检测规则的：两次都恰好 15000ms 的行为，和一个真实用户读 JD、看职位卡、点下一个的行为，形状完全不同。规则 1 要求"慢"，但只有下限的慢仍然是有节奏的慢。

因此 `--delay-ms` 之外增加 `--jitter`（比例，默认 `0` 即关闭）：

```bash
node china-jobs.mjs scan --platform liepin --limit 5 --delay-ms 15000 --jitter 0.4
# 实际每个间隔在 15000–21000ms 之间随机
```

**硬约束**：

- **只增不减。** 抖动是在声明的下限之上再加，不是替换。`--delay-ms` 声明的预算是地板，`--jitter` 只往上加，永远不会突破它。
- **每个间隔重新抽一次。** 启动时抽一次再复用，会得到一个完全可复现的"随机"节奏，比固定间隔更糟。
- **只在真的要等的时候抽。** 一个空闲的 run 不该因为抖动而推迟第一个动作。
- **安全检查的冷却同样抖动。** 被拦截后那段静默期的长度，本身也是信号。
- **越界值夹紧而不是报错。** `--jitter 2` 夹到 1，`--jitter -1` 夹到 0。为一个写错的数字中断整轮采集，比退回下限更糟。CLI 层仍会拒绝 `0–1` 之外的值。

**它不能替代预算。** 抖动降低的是"像不像脚本"的信号强度，不是请求量。上面的 L0–L3 分级照旧，抖动只是让通过预算的那几次请求的**形状**更像人。


任何接口采集脚本，**在第一次请求之前**必须明确声明并写入代码：

| 必须声明 | 示例 |
| --- | --- |
| **总请求数上限** | `MAX_REQUESTS = 20` |
| **请求间隔下限** | `MIN_INTERVAL_MS = 3000` |
| **单次运行时长上限** | `MAX_DURATION_MS = 120000` |
| **遇到风控码时的动作** | 立即停止，不重试、不降级试探 |
| **并发度** | 默认 1（串行），禁止并发 |

### 风控码处理（一律硬停）

| 码 | 含义 | 动作 |
| --- | --- | --- |
| `code:37` | 环境异常 | **立即停止本次运行**，记录，不重试 |
| `code:36` | **账户异常行为** | **立即全局停止**，通知用户，当日不再调用 |
| `code:7` | 登录失效 | 停止，提示用户重新登录 |

**禁止**：遇到风控码后更换 header/cookie/参数继续重试——这既是压测，也是规避风控。

### 站点自愈窗口（等待，不重试）

安全校验由网站自己走完时，采集器**等待**而不是重试。等待期间不发任何指令，请求数增量为 0，因此不计入重试预算，但必须有上限。

| 平台 | 站点 | 等待窗口 | 依据 | 边界 |
| --- | --- | --- | --- | --- |
| BOSS | `/web/passport/zp/security.html?code=37` | **15000 ms** | 2026-10-02 实测该跳约 12 秒由网站自行走完并返回列表；原 8 秒窗口总在完成前一刻到期 | 仅首次列表页允许；进入详情页后安全页仍是终态；全程只允许一次 |
| BOSS（Playwright 路线） | 同上 | 8000 ms | 历史契约，未在原生路线实测 | 同上 |
| 猎聘 | `safe.liepin.com` | **0 ms** | 验证需人工点击，且登录本身会触发账号风控 | 即时终止 |

窗口到期或第二次进入安全页，一律按 `code:37` 处理：立即停止，不重试。

### 接口限流预算（四大厂 provider）

零认证的公开 API 同样受规则 1 约束：慢一点，但**必须比通用 provider 更慢**——它们是同机房后端，不是给脚本用的开放 API。

| provider | 站点 | 页间隔 | 429 退避 | 空响应保护 |
| --- | --- | --- | --- | --- |
| `alibaba` | talent.alibaba.com | **1200 ms** | 3 次 / 1.5s→20s | **有**：后续页返回 HTTP 200 + 空 `datas` 会被当成功吞掉，退避后重试该页 |
| `tencent` | careers.tencent.com | **1200 ms** | 3 次 / 1.5s→20s | — |
| `meituan` | zhaopin.meituan.com | **1200 ms** | 3 次 / 1.5s→20s | 已有 `EMPTY_RETRIES`（原为 400ms 间隔，本次一并放宽） |
| `feishu-jobs` | jobs.bytedance.com | **1500 ms** | 3 次 / 2s→30s | — |

**事故记录 2026-10-02**：四个大厂接口连续探测，前三个正常，飞书下一次请求返回空体。两次单页请求相隔仅数秒，已证明其限流是短窗口且与页大小无关——固定 300ms 间隔无法防御，这也是把间隔提到 1.2–1.5s 的直接依据。

**阿里空响应是最危险的一处**：它的边缘层被限流时返回 `success: true` 但 `content.datas` 为空。若不处理，一次 40 页的整板抓取会在第 2 页被误判为"关键词已到末尾"而静默截断。现已改为：第 1 页允许为空（非真实关键词的正常情况），后续页在满页之后转空则按限流签名重试。

**通用要求**：

- 页间隔跨页、跨关键词生效，首个请求不等待
- 429 必须走 `_http.mjs` 的 `fetchJsonWithRetry`（识别 `Retry-After`、指数退避），**禁止裸 `ctx.fetchJson`**
- 4xx（非 429）不重试——重试一个格式错误的请求只是浪费预算
- 上述每条都有对应回归：`tests/providers/{alibaba,tencent,meituan,feishu-jobs}.test.mjs` 中的 429 / 空响应用例

### 浏览器平台限流预算（BOSS / 猎聘 / LinkedIn）

> **2026-10-02 补记。此前这一层是空的，而它正是风控累积的原因。**

driver 上的 `delayMs` 是**页面就绪等待**（轮询到安全页消失为止），**不是两次平台动作之间的间隔下限**。而 `china/collector.mjs` 的岗位循环原本**完全没有节流**——BOSS 的 `detail()` 正常路径（点击卡片 + 读面板）根本不经过 `wait()`，所以一次采集就是 N 次点击首尾相接。这是把 `_security_check` 计数推到 4+ 的机制性原因，不是偶发。

| 项 | 值 | 说明 |
| --- | --- | --- |
| 动作间隔 | **`--delay-ms`，默认/最低 15000 ms** | 用户声明的预算，逐字生效；覆盖列表页、每个详情页、每次翻页 |
| 首个动作 | 不等待 | 节流约束的是速率，不是启动 |
| BOSS 安全页冷却 | 15000 ms | 与「站点自愈窗口」同值，网站约 12s 自愈，这里只是下限 |
| 猎聘安全页冷却 | **0 ms** | 验证需人工点击，登录本身即可能触发账号风控，driver 直接终止（见规则 2.1） |
| LinkedIn | 同 BOSS | |

**实现**：`china/rate-limiter.mjs`，导出 `createRateLimiter({platform,intervalMs,challengeCooldownMs,now,sleep})`。`now`/`sleep` 可注入，因此全部 9 个测试瞬时完成、不做真实等待。

**关键点**：

- 无论是否需要等待，**每个动作都要打时间戳**。空闲后恢复工作的第一次请求若不记录起点，会与下一个请求首尾相接——限流器会形同虚设（此缺陷由 `pending()` 用例暴露并已修）。
- 遇到安全页时 `noteChallenge()`，冷却从**安全页被看到的那一刻**起算，不是从等待结束起算。
- 连续采集（`china/continuous-collection.mjs`）应把**同一个 limiter 实例**跨轮次传入，否则每轮各自重置时钟，轮次边界仍会紧挨。
### 猎聘额外成本：一个岗位要走两次列表页（2026-10-02 新增）

猎聘的岗位页带有来源绑定：只有「从结果页点进去」才会返回 JD，直接导航到裸 URL 会落到 `safe.liepin.com` 的验证码页。因此 `china/native-page-driver.mjs` 的猎聘分支走 `clickThrough()`——在列表页里找到对应卡片并 `.click()`。

代价是**每采一个岗位要两次列表页**：点击前在列表页，读完详情后必须回到列表页，否则下一张卡片根本不在页面上。`detail()` 里的 `boundUrl!==listUrl` 判断负责这次回退，并用 `lastSignature` 校验列表没有被悄悄换掉（变了就报 `resume_page_changed`，不接着采）。

**因此猎聘的预算按 2× 计**：一次 `scan --limit N` 实际发出的页面请求约为 `2N + 1`（N 次点击 + (N-1) 次回列表 + 1 次首屏），不是 N+1。声明预算时必须按这个倍数折算。

- 429 退避（`providers/_http.mjs` 的 `fetchJsonWithRetry`）**对浏览器路线不适用**：BOSS 和猎聘被限流时返回的是安全页跳转，没有状态码可读，也就无 `Retry-After` 可依。浏览器路线的唯一控制手段就是这个间隔下限。

**回归**：`tests/china/rate-limiter.test.mjs`（9 例）。

### 采集预算分级（2026-10-02 起强制）

触发风控的从来不是单次请求量，而是**单位时间内的请求密度**和**累计总量**。下表把「试」和「采」明确分开，每一级都写死了它的用途和上限。**不允许跨级操作**——想跑大采集，先在普通浏览器里确认账号可用。

| 级别 | 场景 | 命令 | 页面请求数 | 冷却 |
| --- | --- | --- | --- | --- |
| **L0 探路** | 只确认列表页是否可读 | `queue --platform liepin`（不发页面请求） | 0 | 不限，但**每日至多 1 次** |
| **L1 单点验证** | 确认详情页链路是否通 | `--limit 1 --pages 1 --delay-ms 15000` | 4 | 距 L0 ≥ 10 分钟 |
| **L2 小批** | 确认真实产出 | `--limit 5 --pages 1 --delay-ms 15000` | 12 | 距上一级 ≥ 30 分钟 |
| **L3 常规采集** | 日常补充 | `--limit 20 --pages 3 --delay-ms 15000` | ≤ 85 | 单次，不连续 |

`--limit` 最小是 1（CLI 拒绝 0），所以「只看列表页」不能靠 `scan` 实现——`scan` 至少会点进一个岗位。L0 应当走 `queue`（读本地待采队列，不发请求）或直接在普通浏览器里看，两者都不消耗额度。**没有「只读列表」的 CLI 模式**，需要列表页可读性判断时不要用 `scan` 去试。

**硬性约束**：

- **`--delay-ms 15000` 是下限，不可调低。** CLI 已经拒绝更小的值。
- **命中风控立即停，不要重试。** `status: blocked` / `challenge` 之后唯一允许的动作是等冷却，不是再发一次。
- **L0/L1 失败两次即视为账号/IP 不可用**，停止本轮所有平台动作，去人工确认。
- **排障也算请求。** 手动点击、CDP 探针、重复 `list` 全部计入同一额度。
- **BOSS 与猎聘不并行。** 串行执行，各自独立冷却。

### BOSS 的拦截是账号/IP 层面，不是代码问题（2026-10-03 实测）

**先说结论：不要在这个问题上继续改代码。** 三种完全不同的输入方式，同一个页面，同一个已登录会话，结果一致：

| 搜索动作怎么发出去 | 列表页地址 | 之后 |
| --- | --- | --- |
| JS `element.click()` + 原生 setter 赋值 | 到达 `/web/geek/jobs?query=AI%20Agent` | 约 8 秒后弹回 `/`，0 卡片 |
| CDP `Input.dispatchMouseEvent` + `dispatchKeyEvent` | 同上 | 同上 |
| xdotool 真实鼠标键盘（X11 层注入） | 同上 | 同上 |
| **人工在浏览器里手动搜** | — | **同样弹回 `/`** |

最后一行是判据。**手动也过不去，说明 BOSS 拦的是这个出口 IP 或这个账号，不是自动化方式。** 换输入方式、换点击实现、加抖动，都不会改变结果。

**教训（重要，别再犯）**：过程中曾把一次 xdotool 测试判成"成功"——那次坐标偏了 88px，点到的是顶部「海外」导航，落到 `/overseas/` 静态页，那个页面本来就有 20+ 个岗位卡片，和搜索毫无关系。**看到卡片就宣布成功，是把无关页面当成了证据。** 判断搜索是否成功，必须核对 URL 里的 `query` 参数，不能只看卡片数。

**当前状态**：出口 IP `82.153.135.59`（经 mihomo `127.0.0.1:7890`）。账号已登录、无验证码，但搜索被弹回。

**恢复条件**：等风控解除，或换一个未被标记的出口 IP。解封后在**普通浏览器里先手动搜一次**确认能出结果，再跑采集——顺序不能反，否则会重演今天。


BOSS 和猎聘判断的不只是「详情页怎么进来」，还有「**搜索请求怎么发出**」。BOSS 实测：请求 `/web/geek/jobs?query=AI Agent` 并用地址栏直达，**返回的是首页 `/`，零个岗位卡片**；同样的 query 在首页搜索框里输入并点「搜索」按钮，返回正常结果页。

因此三个平台的列表页一律走「打开平台首页 → 定位搜索框 → 填入 → 提交」，实现见 `china/search-box.mjs`（`findSearchBox` / `fillSearchBox` / `submitSearch`）。

**这条规则的两个推论**：

1. **首页是合法落点，但不是万能落点。** `current()` 只在搜索尚未发生时放行平台首页这一个地址；用户真的导航去别处，仍然判 `navigation_changed`。用「不是结果页就放行」会把这个检查整个废掉。
2. **请求预算按「首页 + 结果页」计。** 一次 `scan` 的首屏现在是 2 个页面请求而不是 1 个，L1~L3 的请求数要相应上调。

**实现注意**：填值必须走 `HTMLInputElement.prototype` 的原生 setter 并补发 `input`/`change` 事件；直接赋值 `.value` 页面框架读不到，搜索会按空值提交。

### 预算的记账方式

每次运行结束，记三件事：**出口 IP、时间、页面请求数**。这三样是下次判断「现在能不能动」的唯一依据。没有记录的运行视为已经用掉额度。

## 规则 2.1：猎聘的来源绑定与风控现状

猎聘的岗位页带**来源绑定**：只有「从结果页点进去」才返回 JD，直接 `Page.navigate` 到裸 URL 会落到 `safe.liepin.com`。这不是账号问题，是站点设计——`china/card-click.mjs` 就是为此存在，实测同一岗位两条路径分别得到 1992 字符完整 JD 和验证码页。

| 能力 | 状态 | 证据 |
| --- | --- | --- |
| 来源绑定 | ✅ 已解决 | `findCard` + `clickCard` 走卡片点击，真实 Chrome + 真实 CDP 验证通过 |
| 列表页读取 | ✅ 可用 | 22 个岗位通过规则 17 筛选 |
| 详情页读取 | ✅ 已修复 | 此前 `navigation_changed` / `captured: 0` 的根因就是裸 URL 导航 |
| 出口 IP | ⚠️ 已被封 | 见下方风控升级记录 |

### 风控升级记录（2026-10-02，按时间顺序）

| 阶段 | 出口 | 现象 |
| --- | --- | --- |
| 1 | 直连 IPv6 `240e:37b:…` | `captchaPage_ip_PC`，IP 段被封 |
| 2 | 改走代理 IPv4 `120.39.52.194` | 变成 `captchaPage_PC`（账号级），列表页可用 |
| 3 | 同一 IPv4 出口 | 列表页可读、手动点击可通详情 |
| 4 | 同一 IPv4 出口，约十几分钟后 | 退回 `captchaPage_ip_PC`，**IPv4 也开始被拦** |

**结论**：切换出口只买到了时间，没有解决问题。每一档「解除封禁」都对应累计若干次页面请求，间隔越短、次数越多，回收越快。

**教训（直接约束后续预算）**：

1. 排障性验证也算请求。第 3 阶段里「手动测一下详情能不能通」的那次点击是**真请求**，计入额度——排障不是免费的。
2. 「先用小量试试」必须真的是小量。`--limit 1` 在猎聘上是 3 次页面请求（见上节 2× 折算），不是 1 次。
3. 被封后不要重试。阶段 4 是在已知封禁的情况下又发了一次请求。IP 级封禁不是自愈窗口，撞上去只会加深标记。
4. 先在普通浏览器确认可用，再启动采集；反过来做等于拿采集额度去探路。

**恢复条件**：换用未被封禁的住宅网络出口，并先在正常浏览器确认账号可用，再谈采集。

## 规则 3：优先浏览器路径，不走接口

采集**优先使用浏览器路径**（真实登录态 + 扩展 / 页面内读取），因为它：

- 走的是官方允许的页面上下文；
- 不触发接口层签名校验；
- 风险留痕方式与人工浏览一致。

**接口重放已实测不可行**（见 `docs/career-ops-linux-migration-plan.md` §3.3），且会伤账号。**除非用户明确书面要求并自担风险，否则不使用。**

## 规则 4：采集范围不得缩减

迁移到 Linux 后，采集覆盖**必须与 Mac 上保持一致**：

- BOSS ✅
