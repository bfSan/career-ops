# 国内岗位市场研究与能力路线设计

状态：规划方案；本文件不表示已经开始新一轮采集、生成市场结论或改造代码。

实施主计划：`docs/superpowers/plans/2026-09-10-china-market-workflow-implementation.md`。先完成_custom与4条样表，再按固定schema固化轻量校验和计数；原 `china-market-study` 计划保留为实际采样runbook。

## 1. 目标与交付

用真实、可追溯的岗位样本回答：有哪些工程岗位方向，各方向具体要求什么、做到什么程度，哪些要求共同出现，以及这些证据如何调整个人能力发展路线。

第一期交付是一份市场研究包：采样清单、逐岗要求表、证据校验结果、分组统计、市场报告。第二步才引入个人能力证据，生成路线调整建议。市场提取阶段不读取CV、不按候选人当前能力过滤岗位。

个人目标、城市选择、既有路线来源和样本预算保存在Data Root的 `data/china/research/planning/market-research-brief.md`，不把个人事实写入系统规则。

## 2. 路径选择

| 路径 | 产出和代价 | 决策 |
|---|---|---|
| 先用Codex完成小样本研究，再固化验证和汇总 | 复用已有采集，能先看到真实报告、修正分类 | 第一期采用 |
| 直接把全部JD加入求职pipeline | 可以生成个人匹配报告，但会引入CV、评分、材料生成，且默认要求表存在行数预算 | 个人选岗阶段使用 |
| 先建独立数据库、看板、全自动调度和模型服务 | 后续管理更方便，但当前还没有验证分类与分析规则 | 待两轮研究完成后单独设计 |

第一期不新增MCP服务、浏览器扩展、模型API账号或自动定时任务。可视化先由Markdown表格和CSV承担。

### 2.1 优先复用career-ops的边界

| 环节 | 已有能力 | 本研究如何使用 | 定制范围 |
|---|---|---|---|
| 国内采集 | 本fork的china-jobs、原生driver、版本存储 | 直接使用已验收的BOSS入口 | 这是已经完成的定制开发；日期和薪资仍有后续适配 |
| 本地JD输入 | pipeline支持local:文件，auto-pipeline支持JD文本 | 市场阶段直接读归档；个人评价时用现成入口 | 不另写通用JD抓取器 |
| 要求与证据 | oferta Block B两遍分析、要求重要程度、原文依据 | 复用第一遍JD分析；个人匹配时运行第二遍 | 补市场细分字段、完整覆盖和分组统计 |
| 用户规则 | modes/_custom.md、modes/_profile.md、config/profile.yml | 首版研究流程放_custom；个人事实和目标放既有个人层 | 配置与工作流定制 |
| 能力与学习 | intake、upskill及已知技能排除、学习建议规则 | 有个人证据后整理；个人报告与tracker齐备后运行upskill | 市场证据到路线变更的整理，不复制upskill算法 |
| 岗位比较 | ofertas个人多维比较、oferta单岗评价 | 选定个人目标与候选岗位后使用 | 不把个人匹配排名当市场要求分布 |
| 反馈 | tracker、outcome、interview/debrief、patterns、calibrate | 到真实求职阶段直接复用 | 不新增评分体系或自动调参 |

首版入口优先是 `modes/_custom.md` 中命名的“市场岗位研究”工作流，由Codex按明确步骤执行；本轮仅记录计划，执行时才写入该个人工作流文件。第5节的分析目录是研究输出，不是另建申请tracker。

复用Block B分析规则，不等于直接运行完整oferta并跳过其余约束。市场流程明确只取JD侧分析，个人匹配、全局评分和材料生成仍留在原有个人评价流程。市场要求不得因报告12行展示预算遗漏；这是本工作流的覆盖要求。

原有 `requirement_importance` 包含 requirement、jd_signal、evidence、importance、match。本研究参考它的概念与证据规范，但英语场景、年限类别、AND/OR和冲突等属于新增研究schema，不能宣称既有程序能直接读取。没有个人证据时不伪造match；进入个人评价时由正常oferta产生标准Machine Summary，市场数据不伪装成个人报告。

`upskill.mjs` 聚合tracker关联的已评分个人报告，权重依赖个人匹配分数；它不是无CV的市场频次分析器。第一期市场频次按证据计数，后续具备个人输入时才接它的既有功能。

## 3. 全局约束

- Node >=18、ES modules、现有依赖；不增加运行时依赖。
- BOSS沿用专用Chrome、原生driver、15秒操作间隔；不安装扩展、不复制日常Chrome Cookie。
- 验证、登录或页面异常时停止该批次，不循环刷新或自动切换浏览器方案。
- 采集原文不可改写；每条分析绑定 `jobKey + contentHash`，采集日期不替代发布日期。
- 市场要求提取不读取CV、不按候选人能力预筛、不投递、不沟通、不自动queue。
- 所有研究数据和个人内容放在Data Root的 `data/`、`reports/` 或 `documents/`。
- 第一轮市场统计只计算有原文证据的完整JD；缺失、推测、未完成提取不能作为“没有要求”。
- 当前请求是规划；不启动采集、定时任务、代码实施、Git提交或思源写入。

## 4. 采样方法

### 4.1 三个检查点

1. 现有4条：验证细分维度、替代条件、列表与正文冲突、证据引用。
2. 约20条唯一岗位：形成初步岗位分类及第一版要求表，检查是否遗漏岗位方向。
3. 约60条唯一岗位：在明确采样窗口、城市与方向后生成正式的样本报告；这是执行目标，不是统计代表性保证。

首轮每次最多5条、1页，使用真实搜索URL和15秒间隔。先续跑现有批次；如 `resume_page_changed`，保留旧检查点，明确记录后开始新观察批次，不伪称消费了旧12条待办。每次记录新增、重复、失败数，达到预算或观察到阻塞即停。

搜索词按能力/职责扩展，而非只用一个“agent”：例如 Agent开发、大模型应用、Agent平台、AI基础设施、LLMOps、AI应用架构。词是查询入口，最终岗位分类依据正文；AI基础设施样本可能落在推理/训练方向，应保留分类理由。

研究范围由查询、城市和正文方向限定。不要依据个人年限、英语或当前技能排除样本；明确偏离研究范围的岗位记入排除清单并保留理由。

### 4.2 统计单位

- 主单位是平台岗位ID；相同ID不同内容版本只选本轮冻结的一版。
- 同一岗位命中多个关键词只计一次，但保留全部查询来源。
- 搜索城市与岗位实际地点分别记录；异地、远程、多地点和地点冲突单列。跨城市命中同一ID时总样本仍只计一岗，城市分组规则在manifest明确，不能把搜索筛选城市直接填成岗位所在地。
- 不同ID的相似JD只标记疑似重复；未经证据确认不自动合并。
- 同时展示公司覆盖。匿名雇主不能合并为一家已知公司；匿名、广告、招聘中介分别标记。
- 报告展示各城市/岗位组的有效数量、企业集中情况、详情失败情况和字段缺失情况。
- 这是账户与查询条件下的搜索样本；不输出全平台岗位总量、招聘量增长或真实招聘成功概率。

## 5. 分层数据

`studyId` 采用 `^[a-z0-9][a-z0-9-]{0,63}$`，作为文件夹名。每轮冻结输入，不随store最新值变化。

| 文件 | 职责 |
|---|---|
| `data/china/store.json`、`jds/china/` | 既有采集层；原始岗位、版本和检查点 |
| `data/china/research/<studyId>/manifest.json` | 本轮搜索范围、采样窗口、URL/runId与岗位的关联、搜索城市及工作地分组规则、选取的岗位版本与成功/失败清单 |
| `data/china/research/<studyId>/source-jobs.json` | 冻结的完整JD、列表原文、字段与采集状态；只保存岗位数据 |
| `data/china/research/<studyId>/analysis.json` | 每岗一份结构化市场分析，带来源和分析版本 |
| `data/china/research/<studyId>/validation.json` | 引用、覆盖、枚举与逻辑检查结果 |
| `reports/china-market/<studyId>/<analysisDigest>/requirements.csv` | 可筛选的要求明细；CSV转义并防公式注入 |
| `reports/china-market/<studyId>/<analysisDigest>/market-report.md` | 工具生成的样本、频次与缺失情况；完整分析bundle和summary.json同目录保留 |
| `reports/china-market/<studyId>/<analysisDigest>/interpretation.md` | Codex基于校验后统计生成的方向比较、经验/英语/技能解读和待确认问题 |
| `reports/china-market/<studyId>/<analysisDigest>/route-delta.md` | 有个人证据后生成的路线调整建议；不是市场原始事实 |

### 5.1 分析头与覆盖

每岗分析包含 `jobKey`、`contentHash`、`analysisVersion`、`analyzedAt`、`roleFamily`、`roleFamilyEvidence`、`cityGroup`、`cityEvidence`、`companyKey`、`companyEvidence`、`coverage`、`requirements`、`conflicts`；完整类型以实施主计划第4节为准。bundle携带studyId和sourceDigest，后者覆盖scope与sources；修改范围或输入会使旧分析失效。`roleFamily` 为单一主类，不重复扩大总样本数。

`roleFamily` 使用 application_agent、platform_infra、algorithm_model、engineering_solution、other_technical、unknown。主类只选一个，按主要职责而非搜索词决定；AI架构、高级/初级和细分领域写在要求明细或报告，不新增未定义字段。`roleFamilyEvidence` 包含字段、原文及位置；不明确时选unknown。城市和公司引用允许使用已冻结location/company字段，岗位要求本身只引用description/listingText；不绑定同次观察的列表文本不用于证明旧JD要求。

`coverage` 对每个研究维度使用 `reviewed` 或 `not_reviewed`；只有完整审阅该维度后才写 `reviewed`。没有英语条目且英语维度已审阅，可表述“JD未明确英语要求”；未审阅不能写成零。

### 5.2 要求模型

每条要求保存：

- `id`：岗位内部唯一ID。
- `dimension`：experience、language、skill、education、delivery、domain、work_conditions之一。
- `subject`：例如后端经验、英语口语、Python、Agent生产部署。
- `necessity`：required、preferred、unspecified。
- `evidenceTier`：stated为明确表述，structural为来自任职要求/加分项位置，inferred单独作为分析假设，不进入事实频次或硬要求统计。
- `evidence`：来源字段（description或listingText）、原文引文、起止字符位置；位置采用JavaScript字符串索引，必须精确匹配。
- `levelRaw`：精通、熟练、熟悉、了解等原文；没有则null。不要转换成未经定义的统一能力分数。
- `practice`：从明确职责记录解释、使用、独立开发、生产落地、架构/治理等场景；可多选，不认为每个场景构成统一等级。
- `logic`：single、any、all。Python/Java/Go至少一门是any；“使用某框架或类似系统”也保留替代分支。
- `alternatives`：any/all条件中的具体备选要求，同样保留证据与原文条件；不能把所有选项摊平成必需技能。
- `minimumYears`、`maximumYears`：只从明确年限提取，明确区分总研发、后端、AI、管理及业务领域经验。
- 英语额外记录阅读、写作、听说/会议、客户沟通、证书及使用频率；“英语流利”不自动推断为某CEFR或证书分数。

市场提取保留所有实质要求，不继承个人评价报告的12行展示预算；界面摘要可折叠，完整数据不截断。模型语义判断要与原文分开，程序校验只能确认引用和结构，不能独立证明语义判断正确。

### 5.3 时间、薪资和矛盾

- 分开保存网页发布/更新原文、可确定的绝对日期、观察时间、时间依据。相对时间没有充分精度时保留原文或区间；无字段就是未知。
- 详情写3年以上、列表写经验不限时两者都保留，在conflicts中标记，不静默覆盖。
- 薪资拆分原文、可读文本及证据、币种、计薪周期、区间、薪数、奖金/浮动部分和条件。缺失或编码未解析时不参与金额统计。
- 字体解析与金额归一化是两个问题。现有 `salary-gap.mjs` 不接受 `40-70K·18薪`；市场报告先显示缺失率，金额归一化作为第二期适配。
- 可计算年薪场景必须明确币种、周期、薪数及计算假设；广告薪酬不标为保证实得。未知薪数不默认补12或13。

## 6. 分析输出与验证

报告依次回答：样本从哪里来；岗位分成哪些职责方向；每个城市和方向有哪些经验/英语/技能要求；技能需要在哪类任务中使用；哪些是共同基础、方向专属、加分项；有哪些矛盾和需要向招聘方确认的问题。

统计采用集合去重：同一个技能在同一JD重复出现只计一岗。按主岗位组给出 `n/N` 和具体JD列表，N是该组该维度已完整审阅的岗位数。另列样本总量、未审阅量和未明确提及量。固定必需与“备选之一”分栏；加分项单列，不能把备选技能计成每岗必须具备。

同公司有多个岗位时，同时显示“岗位数/已知公司数”，不让单家公司重复文案被解释为普遍需求。合并城市或岗位组前先展示各组样本结构；不从一次横截面样本推断技能需求正在上升。同城样本配额不能用于比较岗位总量或密度。

校验集从现有JD挑选：列表不限/正文3年冲突；后端3年与总年限区分；至少一门语言；框架或类似系统；Docker/K8s优先；英语未提及；架构落地职责；薪资编码。先人工复核全部4条；扩展20条时复核所有冲突/推断项及至少5条完整记录，后续每批抽查20%。发现系统性误判时重做该规则影响的全部分析。

## 7. 从市场要求到能力路线

市场研究完成后再读既有路线和能力证据。每项能力区分：有可核对证据、用户自述待补证、能力需要验证、已确认短板、与目标方向无关。缺少简历描述不直接判定不会。

路线卡逐项记录：市场依据（岗位n/N和链接）、目标方向、当前证据、需要达到的任务表现、对应作品/项目、验收方法、依赖、投入预算、优先级和复查点。

优先级建议采用可解释分层：目标方向共同门槛且已确认缺口优先；能直接复用已有经历形成证据其次；特定方向专属能力按选定路线安排；只有个别加分样本的方向先观察。招聘需求频率不是学习价值的唯一指标，基础依赖、个人目标和投入成本也要显式说明。

输出最近2周的具体任务、随后4周的里程碑、较远阶段的候选任务。验收以作品和独立解释/操作为单位，不以课程看完为单位。每两周对照新样本及真实实践反馈更新一次，保留变更理由，不自动改写原路线。

## 8. 分工与后续子项目

- BOSS适配器：取得完整原始证据、保存版本和检查点。
- 第一市场研究流程：全文要求拆解、证据检查、样本汇总；复用career-ops的要求/证据思想。
- career-ops个人分析：目标确定后做个人匹配、材料、面试和实际结果复盘。
- 思源：保留既有路线、学习笔记、项目证据和经确认的新路线；本轮只读。

实施主计划在4条样表验证后安排轻量JSON校验与统计CLI，首轮市场研究覆盖用户指定四城。后续独立子项目：发布日期与国内薪资适配、猎聘真实JD及跨平台对照、思源写回、周期工作流和看板；各自验收，不推迟已有JD的要求分析。
