# 求职分析要素配置：优先复用 career-ops

状态：配置与工作流已实施，15 条代表岗位验证通过。2026-09-13。全量细分类审阅与公司身份/核心业务核验尚未完成，覆盖见[首次验证报告](../../../reports/china-market/analysis-factors-2026-09-13/README.md)。

本稿替换上一版“新建 career-analysis 子系统”的首期方案。用户指出应优先配置分析要素；核对现有入口后，配置与工作流已足以开展当前分类研究，暂不新增分类引擎、CLI 参数或选岗子命令。

## 1. 现有能力核对

| 需求 | 已有入口 | 实际支持范围 |
|---|---|---|
| 每次分析哪些内容、采用什么规则和报告格式 | `modes/_custom.md` | Agent 在执行模式时读取的持久工作流指令，可要求额外分析要素并引用研究简报 |
| 个人目标岗位、archetype、叙事和评价偏好 | `modes/_profile.md`、`config/profile.yml` | 原有个人评价配置；市场研究分类不等于候选人自己的目标或已掌握能力 |
| 关注招聘公司及扫描来源 | `portals.yml` | 原有 tracked_companies/job_boards、链接及过滤配置；实际可采性取决于对应 provider/ATS |
| 四城市场分析范围和方法 | `data/china/research/planning/market-research-brief.md` | 当前 `_custom.md` 已明确要求读取；可直接补充分析要素、分类定义、关注对象和输出要求 |
| 公司类型、领域、职能、级别 | `modes/_shared.md`、`modes/oferta.md` | 当前代码库已有公司类型及薪资可信度规则，Block A 已包含 Domain/Function/Seniority，Block B 已有要求—个人证据对照 |
| 技能、要求条件、薪资日期、归档回读 | 已有 market、skill-extract、compensation、posting-dates、provider/source 模块 | 继续复用，不为新的分类词修改采集器 |

关键区别：这些 Markdown 配置由 Agent 阅读并执行，不是“随意增加 YAML 字段后所有 Node 脚本自动识别”。`china-market.mjs` 的六个粗类和七维分析 schema 仍为固定契约；新增业务/职能细分首期体现在附加分析结果中，不直接塞入旧 analysis.json。

## 2. 首期只配置研究要素

以现有 `_custom.md` 为入口，把具体要素和判定规则集中在已有市场研究简报中，不在两个地方重复维护分类定义。

### 公司要素

- 招聘主体、展示品牌、服务客户分别判断；外包客户不能当作招聘主体。
- AI 原生属性：是、否、无法确认；依据核心业务与公司资料，不能以名字或 JD 提到某模型判断。
- 业务层：基础模型、生成媒体、AI 应用/Agent、AI 基础设施、互联网业务、企业技术产品、行业内部应用、技术交付、科研等，可多选。
- 行业与业务场景分别标注，如制造业/采购、金融/投研、网络产品/设备运维。
- 公司规模、所有制、上市与阶段独立标注；信息缺失就保留未知。
- AI 原生重点关注对象：DeepSeek、MiniMax、月之暗面/Kimi、智谱、阶跃星辰；硅基流动作为基础设施方向观察对象。名单是研究偏好，不是客观名次或在招证明。

### 岗位要素

按正文主要交付成果选一个主类，可附有证据的次类：

1. 模型与算法研究。
2. 研究工程与后训练。
3. 训练与推理系统工程。
4. AI 平台与基础设施。
5. AI 应用与 Agent 研发。
6. 数据与知识工程。
7. AI 评测与质量工程。
8. 解决方案与交付实施。

另列其他技术/无法判断。技术领域、职级与管理职责是独立标签。岗位标题只是线索，不把研究工程师一律归研究，也不把所有 AI 原生公司岗位归研究。

### 要求要素

继续复用现有技能、经验、语言、学历、交付、领域与工作条件分析。展示必须/加分/任选关系，技能程度、总研发/AI/领域/管理经验、英语实际使用场景及上线/研究/性能等成果证据。

分类、公司关注点不能产生 JD 没有写过的硬性要求，也不能自动成为个人缺口或已知能力。

## 3. 工作流中的实际使用

在当前市场工作流中增加配置指令：读取简报 → 回读归档 JD → 按要素逐岗分析并保存依据 → 运行现有 connect 获取已有统计 → 将新增公司/职能分类结果与现有要求按 jobKey/contentHash 关联 → 生成公司业务 × 岗位职能的补充报告。

逐岗分类可以保存为一份研究输出表或 JSON，包含来源版本、分类、原文/官网引用、判断理由和未审阅/未知/冲突状态。它是本次研究的结果，不是新建程序子系统或旧 analysis schema 的升级。

计数由脚本从已审阅结果计算，不由模型心算。优先使用现有统计能力；新增分类交叉表如确需脚本，只补小范围研究脚本，并明确它不是原有 connect 已支持的新字段。后续多次复用且格式稳定后，再考虑通用化。

用户在日常使用中可以直接改简报中的字段、类别定义、关注公司和输出要求；不需要为增加一个分析因素修改 Node 代码。每次报告保留当次使用的规则和源版本，便于解释变化。

## 4. 输出与验证

- 公司业务 × 主职能：广告数、已辨认公司数、匿名/未审阅数。
- 各组技能及要求：区分关键词提及与明确门槛，保留原文和适用分母。
- 年限、语言、项目深度及薪资：使用对应字段有证据的样本，不将公司类型差异解释成因果。
- AI 原生关注覆盖：已采到、未采到、入口未打通、工作地点不符分别显示；未采到不代表无招聘。
- 四城样本与重点公司对照样本分别展示，集合交集去重；总部不代替岗位所在地。

首先用已有代表岗位验证配置：阿里云的记忆与平台、锐捷的 Agent 应用、迈富时的 Coding Runtime、鱼跃的 RAG、美团评测、福耀数据、佳期基础设施及匿名/外包案例。确认方法有效后扩到190条；不能把尚未审阅的记录声称为分类完成。

当前已有98条七维要求完整审核，92条待审核。配置新增分类不会改变这一事实，也不修改最新报告或原始 JD。

## 5. 个人求职衔接

用户选择进入个人阶段后，既有 pipeline/oferta 使用这些分析结果辅助理解岗位。Block A 展示公司、领域和职能背景，Block B 保留唯一的要求—真实个人证据表；个人 archetype 与评分仍按真实目标和原有规则执行。

有真实评分报告和 tracker 后继续用聚合 upskill。单岗 upskill 可读取 JD，但词汇结果不替代语义条件及实践深度判断。不给 profile.yml 填入市场关注技术清单来冒充候选人能力。

公司招聘入口确认且对应采集能力可用后，再加入原有 portals.yml；配置公司名本身不会实现官网解析。第一期不改 BOSS/猎聘、Cookie、扫描策略或任何个人投递记录。

## 6. 何时才需要通用代码

仅在反复运行后出现以下具体需求时补开发：

- 固定 CLI 必须直接按任意新要素筛选或生成交叉统计。
- 新字段必须被 Machine Summary、upskill 或其他消费者程序化读取。
- 多批次分类已稳定，需要通用 schema 校验与跨批比较。
- 招聘官网现有 provider 无法读取，需要增加来源适配。

届时开发通用的“读取要素定义—校验结果—分组输出”能力，标签与分类仍在用户配置中；不为金融、原生AI、某家公司或某岗位类型分别写规则分支。

## 7. 本轮实施结果

- 已将范围、公司业务/身份、AI 原生关注名单、8 类职能、要求条件和输出口径集中到现有研究简报，更新 `_custom.md` 的读取与执行流程，并补充使用文档。
- 已从当前研究选择 15 条冻结 JD 实际执行：13 条职能可分类、2 条职责不足；175 条待新规则审阅。岗位服务业务 9 条可判断、6 条未知；未将它们外推为公司整体属性。
- 64 段原文引用精确校验通过，64 个篡改引用被拒绝；31 个报告/文档本地链接有效。已有 190 条通过临时隔离数据根的 provider → pipeline → 全文回读，重复导入增加 0 条。
- 原始 JD、store、冻结研究和当前主报告共 353 个文件内容保持不变。原有七维完整审阅仍为 98 条，92 条待审阅；本次要求抽查不提升该覆盖数。
- 6 个关注对象在 190 条公司展示字段中均未匹配到配置中的名称线索；法人别名及公司核心业务尚未核验，未据此推断无招聘。

本轮在当前会话完成，无子 agent；未新增生产分类代码、CLI 或 provider 分支，未改个人资料或投递记录。后续按同一配置扩展数据审阅；如新增要素仅影响分析方法，继续更新用户配置。
